# Claude Code 独立实现：网络层验证记录

## 验收目标与当前状态

用户已进一步明确：**不需要原生工具与完整提示词，目标是正确发送客户端特征请求并让第三方网关接受**；运行时继续完全独立于 CLI 文件。下面新增限定范围的验收，保留之前完整正文对照的历史记录，不把两者混为一谈。

当前 **3.0.0-beta.2** 保留 NextChat 提示词与工具，使用独立网络组件。已通过本地客户端特征对照与初始 ClientHello 检查。它不承诺“无法被识别”或“任意网关接受”；连接复用、会话恢复、重试及其他协议分支尚未完成 CLI 对照，也没有目标第三方网关的实际接受结果。

实现由 **SDK 2 + 可安装插件 + 独立 Windows 发包程序** 组成，接入聊天、工具续接、辅助请求和模型列表。使用方式见 [独立发包组件](wire-relay.md)。真实 CLI 只用于开发时获取参考数据。

## 当前范围：客户端特征检查

以之前两轮真实交互式采集中第一条请求及独立插件请求为依据，`compareClientSurface` 的 9 项检查通过：请求行及头的顺序、大小写、值和空白；非应用内容的协议字段及序列化顺序；billing/身份块；系统与最后消息的缓存结构；消息与系统块格式；头与 metadata 的会话一致性；设备标识格式。Content-Length 的值允许随正文变化，但必须与实际 UTF-8 字节数相符。

明确不比较：消息正文和运行时提醒、第三个系统块中的应用指令、工具定义及工具环境 safeguards。**这是按产品用途限定的测试范围，不是已知的网关检测规则。** 网关若检查这些内容仍可能拒绝请求。

3.0.0-beta.2 的默认请求输出与已采集的 beta.1 保持逐字节相同，安装包回归检查固定这一点。新增自定义版本标记必须显式选择未验证配置，网络组件仍使用同一固定构建，不把版本字符串变化标为新版本验收通过。

完整正文比较器仍保留原来的失败结果；新增检查不会将失败改写为“整个 CLI 等价”。初始 ClientHello 由实际编译产物独立检查，其他网络行为和第三方网关接受情况分别记录，不能根据其中一项推断其余项通过。

以下章节保留此前更严格的完整请求研究结果。

## 已验证的事实（2026-11-11）

参考客户端为 Windows x64 的 Claude Code 2.1.322，启动标准交互式会话，没有使用 `--print`。它内嵌的运行时标记为 Bun `1.4.4+424a542a9c79d679fcdacc37a52d4fb2134408ca`。

候选运行时从官方 npm 包 [@oven/bun-windows-x64 1.4.4](https://registry.npmjs.org/@oven/bun-windows-x64/1.4.4) 获取，下载时验证了 registry 提供的 SHA-512 integrity，独立解包到测试目录，未进行全局安装。它报告的构建号为 `1.4.4+38afee6c84fcf48c0edb2466aa4b27d287a59c30`，运行测试不使用 Claude Code 文件。

| 路径                                         | 初始 ClientHello 稳定字段 | HTTP 请求字节            |
| -------------------------------------------- | ------------------------- | ------------------------ |
| Node 24.13.0 fetch                           | 与参考不一致              | 未在此实验比较           |
| Bun 1.3.14 fetch                             | 与参考不一致              | 未在此实验比较           |
| 独立 Bun 1.4.4 fetch，传入小写头名称         | 与参考一致                | 头顺序和大小写不一致     |
| 独立 Bun 1.4.4 https.request，传入原始头列表 | 默认 TLS 配置不一致       | 捕获请求的回放一致       |
| 独立 Bun 1.4.4 fetch，保留原始头大小写       | 与参考一致                | 捕获请求的回放逐字节一致 |

ClientHello 比较保留了 TLS 记录长度、版本、密码套件及顺序、扩展及顺序、曲线、签名算法、ALPN、key-share 类型与长度。只排除了每次握手本来就变化的随机字节、会话 ID 值和公钥字节，并规范化 GREASE 值；保留这些字段的结构和长度。参考 CLI 的五次握手在这些字段上相同。

HTTPS 测试使用本地证书，通过子进程的 `NODE_EXTRA_CA_CERTS` 指定信任；没有关闭证书验证，也没有修改系统证书库。服务端同时提供 h2 和 http/1.1，参考客户端及独立候选在本次测试中都选择 http/1.1，协商 TLS 1.3 / TLS_AES_256_GCM_SHA384。

最后一条路径回放的 HTTP 请求为 **98,470 字节**，方法、路径、头名称大小写、头顺序、字段值和请求体字节全部相同，正常收到模拟 SSE 回复。对照摘要与完整规范化 ClientHello 位于 `test/fixtures/claude-wire-2.1.322-windows.json`。这次实验的完整临时请求已随 `.next` 构建清理；它不能用作可重新检查的原始证据。下述新采集工具将完整请求保存在独立的系统临时目录，避免构建覆盖。

## 安装包完整请求对照（2026-11-11）

使用仓库内的新采集工具，重新启动真实 2.1.322 交互式 CLI，向本地模拟网关发送两轮文本。随后关闭 CLI，直接加载 **3.0.0-beta.1 安装包**，从第一条用户文本、相同模型和明确配置的设备/会话身份生成请求，经独立编译产物发送到同一网关。没有将原始 CLI 的 system、tools、reminders 或 safeguards 复制给插件。

结果：**完整请求对照失败**。参考请求为 **98,245 字节**，插件为 **1,906 字节**。请求行和除 Content-Length 外的头字段、大小写及顺序相同；正文差异在环境提醒、第三个系统块、原生工具定义和 safeguards。Content-Length 随正文变化，因此整段头字节也不相同。此结果验证了原生提示词与工具的缺口确实存在，不能用先前的回放成功代替独立生成验收。

| 项目                        | 结果                                                     |
| --------------------------- | -------------------------------------------------------- |
| 全量应用测试                | 98 套、751 项通过                                        |
| 网页生产构建                | 通过，存在原有 lint 警告                                 |
| 桌面静态前端构建            | 通过；未据此声称 Tauri 原生安装包已验收                  |
| 独立发包程序集成测试        | 8 项通过                                                 |
| 完整请求比较器测试          | 3 项通过，覆盖缺字段、头大小写/顺序、JSON 顺序与脱敏输出 |
| 插件完整请求与真实 CLI 比较 | **失败，未达到严格要求**                                 |

复现步骤见 [交互式采集与对比](interactive-request-parity.md)。比较器不忽略凭据、ID、提示词或其他字段；这些值需要由测试场景显式对齐。报告只输出差异路径、长度和哈希，不打印完整字段值。原始捕获保留在本地，不进入版本库。此 HTTP 采集服务不采集 TLS；TLS 基准由独立网络集成测试检查。

## 这些结果尚不能证明什么

1. **请求生成尚未相同。** 成功回放使用了参考 CLI 已生成的请求体。它不能证明现有 NextChat 插件能从任意用户输入生成相同内容；原有提示词、工具定义和环境状态的差异依然存在。
2. **连接生命周期尚未验证。** 测试中观察到 CLI 后续连接恢复了 TLS 会话，快速回放则复用了现有连接。需要在相同请求时序及流消费方式下重新比较，不能把它们直接判为一致或不一致。
3. **协议分支尚未覆盖。** TLS 1.2、不同证书与服务器协商、HTTPS 代理、重定向、取消、超时、重试、压缩及长连接均需独立验收。
4. **平台不能外推。** 当前仅有 Windows x64 证据，不能据此认定 Linux、macOS、其他 Bun 构建或其他 CLI 版本相同。

因此，不能继续使用 NextChat 的普通 fetch/reqwest 通道作为严格模式的发包层，也不能只改 User-Agent。候选结构应是“版本化请求生成插件 → 独立且固定构建的网络组件 → 上游”。网页与桌面都交由该组件发送上游请求，原始头名称和序列化后的请求字节必须在中间通道保持不变。

版本配置必须绑定整套已验收的生成规则、运行时及平台配置；不能把任意版本字符串标成已验证。完整同版本请求生成逻辑和上述网络分支通过对照之前，不发布或命名为“完全一致”模式。

## 排除的方案

实验还发现 `BUN_OPTIONS --preload` 能让本机 Claude Code 可执行文件内嵌的运行时执行独立代码并在 CLI 主程序前退出。这仍依赖 CLI 文件，**用户已明确拒绝该依赖，不用于产品实现**。也不采用 `--print`、后台真实 CLI 会话或静默回退来代替独立实现。
